Executive summary

Current model (post multi-connection, PR #405, Dec 2025) One embedded engine per process, bound to one data path. Multiple native connections/sessions to that same path can be open and execute queries concurrently. Opening a different path while the engine is active returns an error.
Workload Advertised approach
One-off / file queries Stateless query API (chdb.query, Rust execute)
Stateful / repeated analytics One long-lived, file-backed session; load once, query many times
Concurrent server-like workloads Pool of connections/sessions to the same path (Go: SetMaxOpenConns)
Multi-threaded, one session Engine: thread-safe queries; Ruby: share one Database; Python DB-API: one connection per thread
Documentation is inconsistent Python ReadTheDocs and the libchdb C header still say “one connection/session per process.” chdb-go README, chdb-core concurrency tests, and observed behavior in chdb-rust examples contradict that for same-path multi-connection use.

Session lifecycle best practices

What a session is

A chDB session is a native connection + data path. Sessions preserve state across queries: tables, inserts, temp objects, and settings. The engine is embedded in your process — this is not a client/server database with external connection limits.

1. One-off queries — no long-lived session

Use the stateless API when you do not need persistent tables:

  • Python: chdb.query(...)
  • Go: chdb.Query(...)
  • Rust: execute(...)

Best for querying files, URLs, or simple in-memory analytics. Do not open a session unless you need state.

2. Stateful / repeated work — one long-lived session

When you create tables, insert data, or run many queries against the same embedded database, docs consistently recommend reusing one session (especially file-backed) rather than reopening per query. 

# Python — persistent session for repeated analytics
from chdb import session as chs

sess = chs.Session("/path/to/analytics.chdb")
sess.query("CREATE TABLE users AS SELECT * FROM file('users.parquet', 'Parquet')")
result1 = sess.query("SELECT COUNT(*) FROM users WHERE age > 25")
result2 = sess.query("SELECT AVG(age) FROM users GROUP BY department")
sess.close()  # or use a context manager

Storage choices:

  • Session() / no path — temp directory, auto-cleaned when session closes
  • Session("/path/to/db") — persistent across restarts

3. Concurrent workloads — connection pool, same path

From the chdb-go README (most explicit current guidance): 

db, err := sql.Open("chdb", "session=/path/to/data")
db.SetMaxOpenConns(8)  // each pooled conn = independent native connection, same path

chdb-go NewSession docs: multiple sessions can be open if they share the same data path; each owns an independent native connection and can run queries in parallel.

4. Multi-threaded sharing of one session

BindingGuidance
Ruby Share one ChDB::Database across threads; read/write on that instance are thread-safe. new/open/close are not thread-safe — synchronize lifecycle calls.
Python DB-API threadsafety = 1 — share module, not connections; one connection per thread.
chdb-core tests test_sessions_are_thread_safe: one shared session, 3 threads concurrent INSERT — no errors, 9 rows inserted.

What not to do

Anti-patternWhy
Open a second different path without closing the first Runtime error: engine already initialized with another path
Leave streaming queries open May block other queries; always close or use context managers
New temp session for every repeated query on same data Troubleshooting/perf docs recommend persistent session + tables instead
Pool of different database paths in one process Not supported — one engine/path per process

Resource management (all bindings)

  • Close sessions/connections on shutdown
  • Use context managers / defer / RAII where available
  • Always close streaming results on early termination
  • For large datasets: file-backed sessions + streaming queries

Session lifecycle decision tree

Need persistent tables / repeated queries on same data? ├─ No → stateless query API (execute / chdb.query) └─ Yes → file-backed Session, kept for app lifetime │ Need concurrent queries? ├─ No → one Session, reuse it └─ Yes → pool of Sessions/connections, same path (Go: sql.Open + SetMaxOpenConns) (Rust: multiple SessionBuilder::build() on same path)

Per-interaction sessions?

Default answer: no. Reuse a long-lived session for stateful/repeated work. For concurrent apps, spinning up sessions per worker/request is fine if they share the same path and are managed as a pool — not opened and torn down on every single query when avoidable.

From chdb.h shipped with libchdb (what chdb-rust links):

On chdb_connect — likely stale

/**
 * Creates a new chDB connection.
 * Only one active connection is allowed per process.
 * Creating a new connection with different path requires closing existing connection.
 */

On chdb_query / chdb_stream_query — still relevant

/**
 * Executes a query on the given connection.
 * Thread-safe function that handles query execution in a separate thread.
 */

The “one connection per process” comment conflicts with chdb-go docs and chdb-core tests. Treat query-level thread safety as accurate; treat the one-connection limit as outdated (now: one path per process, multiple connections to that path).

Read-during-write visibility

Not explicitly documented chDB does not document MVCC/snapshot isolation for concurrent streaming reads. An active stream may not observe rows inserted mid-stream (consistent with ClickHouse query snapshot semantics), even though inserts succeed and final COUNT() reflects new rows. See test_streaming_query.py (test_multi_thread_streaming_query) for stress-test behavior, not formal isolation guarantees.

Streaming-specific guidance

From chdb-core/docs/streaming.rst:

  • Use context managers or explicit close() on streaming results
  • Call close() on early termination — do not rely on GC alone
  • Arrow streaming is typically faster than CSV for large numerical datasets
Warning from streaming docs “Streaming queries may block other queries if not properly closed.” Implies same-connection interaction risk; use separate sessions for overlapping work when possible.

Concurrent streaming + inserts are exercised in test_streaming_query.py with separate sessions per worker thread.

chdb-rust-specific notes

  • Uses SessionBuilder for persistent state; execute for stateless queries
  • Session and Connection are Send but not Sync — share across threads via Mutex (or one session per thread)
  • QueryStream borrows the session connection for its lifetime — only one active stream per session in safe Rust
  • Crate docs recommend synchronizing concurrent access to the same session
  • Test suite note: run with --test-threads=1 due to connection resource contention in some environments
  • Concurrency examples 11–16 in examples/ demonstrate same-session vs multi-session patterns
// Long-lived app session (production-shaped)
let session = SessionBuilder::new()
    .with_data_path("/path/to/analytics")
    .with_auto_cleanup(false)
    .build()?;

// Ephemeral scratch session (demo / test shaped)
let session = SessionBuilder::new()
    .with_data_path(temp_dir)
    .with_auto_cleanup(true)
    .build()?;
