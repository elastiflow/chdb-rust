Review: Concurrency Examples 11–16

Effectiveness review of chdb-rust streaming concurrency examples, with recommendations for clearer verification that concurrent access works as intended — especially that writes do not pollute in-flight reads.

Executive summary

Examples 11–16 form a coherent progression from serialized same-session reads through fully overlapping reads and writes. All examples correctly use execute_stream rather than materializing full results, and shared setup in concurrency_common.rs keeps them consistent.

When run locally (macOS arm64, libchdb v26.5.0), every example completed without error. Readers consistently observed 300,000 rows even when 1,000-row inserts completed mid-stream, and final row counts matched expectations after concurrent writes — behavior consistent with query-time snapshot semantics, as noted in the concurrency reference doc.

Main gap: Examples 13, 14, and 16 report read row counts but do not assert them. A regression that let writes pollute active streams could pass silently in 13 and 14; example 16 would still pass if only write counts were checked. Row-count-only checks also miss partial pollution (e.g. a few inserted IDs appearing mid-stream).

The highest-value improvements are: (1) assert snapshot isolation where reads overlap writes, (2) spot-check streamed data (min/max n, or a sentinel row), and (3) fix example 12’s overlap heuristic so parallelism is demonstrated reliably.

Example 11 — concurrent reads, same session

Source: 11_concurrent_reads_same_session.rs

What works

  • Correctly documents why Arc<Mutex<Session>> is required (Session is Send but not Sync, QueryStream borrows the connection).
  • Each thread performs a full streaming read via spawn_streaming_read.
  • expect_row_count fails the example if any reader returns ≠ 300,000 rows.

Observed output

Per-thread read time ≈ 12–14 ms; wall time ≈ 40 ms (≈ sum of three serialized reads). This confirms mutex serialization, but the example never states that comparison explicitly.

Recommendations

  • Print and compare wall_elapsed to sum(outcomes.elapsed) with a message like “wall ≈ sum → reads ran one-at-a-time on this session.” This is the intentional negative control for example 12.
  • Optional: in the first chunk, parse one JSONEachRow line and assert {"n":0} (pattern from 08_query_streaming.rs).

Example 12 — concurrent reads, different sessions

Source: 12_concurrent_reads_different_sessions.rs

What works

  • Each thread owns a session on the same path — the recommended concurrent pattern.
  • Row counts validated with expect_row_count.
  • Cleanup of temp data path on success and failure.
Bug in overlap heuristic: The check at lines 52–55 compares wall time to the average per-thread elapsed time. On a local run, wall ≈ 27 ms and average ≈ 26 ms, so the “indicating overlap” message never printed — even though per-thread read time was ≈ 13 ms and three reads clearly overlapped.

Recommendations

  • Replace the heuristic with: wall_elapsed < sum_elapsed * 0.8 (or simply wall_elapsed < max_elapsed * 1.5).
  • Print all three numbers: wall, sum, max — makes the proof visible at a glance.
  • Optionally assert wall_elapsed < sum_elapsed / 2 for three readers as a hard check.

Example 13 — write during a single streaming read

Source: 13_write_during_single_read.rs

What works

  • Good coordination: writer waits for reader’s first chunk before inserting (lines 46–48).
  • Separate sessions for reader and writer — required because a single session cannot interleave stream + write in safe Rust.
  • Reports streamed_rows, final_count, and write outcome.

Observed output

Reader streamed 300,000 rows; writer inserted 1,000; final count 301,000. The reader did not see the new rows — the key isolation property — but the example only prints a hedged note (“may or may not have seen new rows”) and returns Ok(()).

Missing assertion: This is the most important read/write isolation example, yet it never verifies streamed_rows == ROW_COUNT or final_count == ROW_COUNT + WRITE_BATCH_SIZE.

Recommendations

  • Assert streamed_rows == ROW_COUNT and final_count == ROW_COUNT + WRITE_BATCH_SIZE; fail with a clear message if not.
  • Track max_n while draining chunks (parse JSONEachRow "n": values). Assert max_n < ROW_COUNT (inserts start at ROW_COUNT + 1 per insert_start). This proves writes did not appear in streamed data, not just that the row counter stayed at 300k.
  • Log row count after first chunk vs at stream end — if they differ, pollution occurred mid-stream.
  • Remove unused started variable in the writer thread (compiler warning).

Example 14 — write during concurrent streaming reads

Source: 14_write_during_concurrent_reads.rs

What works

  • Waits for all CONCURRENT_READERS to signal first chunk before writing.
  • Three independent streaming readers, one writer — realistic overlap scenario.

Observed output

All three readers streamed 300,000 rows; writer inserted 1,000; final count 301,000. Example exits Ok(()) unconditionally.

Recommendations

  • Apply expect_row_count to each reader (same as examples 11/12).
  • Assert final_count == ROW_COUNT + WRITE_BATCH_SIZE.
  • Optionally report whether readers disagreed on row count (would indicate inconsistent snapshots).
  • Per-reader max_n tracking — all should stay below ROW_COUNT.

Example 15 — concurrent writes

Source: 15_concurrent_writes.rs

What works

  • Disjoint insert ranges prevent primary-key collisions (start = ROW_COUNT + 1 + i * WRITE_BATCH_SIZE).
  • Hard assertion on final count (lines 73–77).
  • Error propagation from any failed writer.

Recommendations

  • Post-write spot check: SELECT min(n), max(n) FROM num WHERE n > ROW_COUNT — confirms all three batches landed in expected ranges.
  • Print sum(writer elapsed) vs wall time to show write parallelism (mirror of example 12).

Example 16 — concurrent reads and writes

Source: 16_concurrent_writes_during_concurrent_reads.rs

What works

  • Barrier ensures all 6 workers start together — strongest overlap guarantee in the set.
  • Write side fully verified (final count assertion).
  • Combines patterns from 12, 14, and 15 into one stress scenario.
Read side unverified: All three readers returned 300,000 rows in a local run, but the example never calls expect_row_count. It would pass even if every reader saw 303,000 rows (write pollution) as long as the post-hoc COUNT() matched.

Recommendations

  • Add expect_row_count for every read outcome — highest priority fix here.
  • Assert all readers agree on row count.
  • Consider per-reader max_n during stream as in example 13.

Cross-cutting recommendations

1. Shared helpers in concurrency_common.rs

Add to concurrency_common.rs:

  • max_n_in_chunk(data: &str) -> Option<u64> — parse JSONEachRow lines.
  • expect_snapshot_read(rows: u64, max_n: Option<u64>, label: &str) — assert rows == ROW_COUNT and max_n < ROW_COUNT.
  • print_timing_summary(wall, outcomes, mode) — “serialized” vs “parallel” interpretation.
  • expect_final_count(session, expected) — unify post-run verification.

2. Sentinel-row technique (strongest content proof)

Before starting concurrent reads, insert one row with a distinctive value (e.g. n = 999_999_999) via a separate session. Active streams querying ORDER BY n over the baseline range would never encounter it; a polluted read might. Lighter than scanning all chunk JSON, and very readable in output.

3. Chunk-boundary logging

When the write completes, log each reader’s cumulative row count at that moment (requires shared atomic counters updated per chunk). Proves the write happened during streaming, not before or after.

4. Automated smoke tests

No test harness currently runs examples 11–16 (see tests/examples.rs). A #[test] that runs each example binary and checks exit code 0 would catch regressions. Note the existing guidance to use RUST_TEST_THREADS=1 due to libchdb contention.

5. Smaller table for CI, same semantics

ROW_COUNT = 300_000 makes examples slow in CI. A #[cfg(test)] or env-var override (e.g. CHDB_EXAMPLE_ROW_COUNT=10_000) would preserve semantics with faster feedback, without changing the default demo experience.

6. Document expected outcomes in module docs

Each example’s //! header should state expected results explicitly, e.g.: “Reader sees exactly 300,000 rows; final count is 301,000; max observed n is 299,999.” Aligns with streaming guidance in the concurrency reference.

7. Other angles not yet covered

  • Same-session write during stream (expected failure / block): Demonstrate that attempting an insert on the session that owns an active QueryStream fails or blocks — reinforces why examples 13/14 use a second session.
  • Early stream drop: Per chdb-core streaming docs, unclosed streams can block other queries. An example that drops a stream mid-read then writes would complement the happy path.
  • Arrow streaming variant: Repeat example 13 with 09_query_streaming_arrow.rs / 10_arrow_query_stream.rs to confirm isolation holds across output formats.
  • Negative control: A reader that starts after the write should see ROW_COUNT + WRITE_BATCH_SIZE rows — proves the insert actually landed and contrasts with snapshot reads.
